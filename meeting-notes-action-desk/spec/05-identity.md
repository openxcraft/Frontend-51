## Typography (P07 — Readex Pro + DM Sans)

- **Arabic: Readex Pro** (real weights 300/400/500/600/700 — a variable bilingual family) — the P07 point is that ONE family carries both scripts with matching proportions; Arabic renders Readex Pro everywhere. Body ≥15px equivalent in register rows; 16px+ in notes/capture reading surfaces.
- **Latin: DM Sans** (real weights 400/500/700) — chrome and Latin body; Readex Pro's own Latin companion glyphs render inside mixed-script strings (bidi-isolated runs) so a code-switched line keeps one voice instead of visibly switching horses mid-sentence. 500 for table headers and action titles; 700 for the single H1 per screen.
- Line-height: Arabic 1.6 body / 1.4 headings (tashkeel headroom reserved on capture segments that carry diacritics — rtl-rules §3); Latin 1.5. Tracking 0 for Arabic everywhere (token-level build rejection otherwise). No synthetic bold on missing weights (Readex Pro 600 exists; if an implementation binds a static subset, re-bind to 500/700).
- **Numerals: Western** (ledger row; data surface per design-language-map §7): dates, due dates, counts, respond-by countdowns, register cells all 0-9; Arabic-Indic numerals never appear in system chrome (storage canonical, display formatted). Arabic copy strings render Western numerals inside Arabic text (e.g. "استحقاق 26 أكتوبر") per the ledger's Western policy.
- One pairing for reading AND chrome (T3 discipline; no third family; no monospace — timestamps and IDs render at tabular-figure settings where the implementation supports it).

## Shape, elevation, iconography, motion

- **Density B (standard, 6–10px)**: cards 8px, register rows 6px, chips and composer inputs 6px. Declared deviation: fully-rounded removable filter chips ONLY (P08 semantics) — recorded here, all other radii in the B family.
- **Elevation: soft-lift**: one diffuse ambient shadow step (card over canvas), paired with the canvas→raised surface step; modals lift one further step with scale 0.96→1.0 + fade at 140ms (motion-language §3). Shadows never carry meaning (state is color+text+glyph), never stack more than two steps, and the confirmation state change is NOT a shadow change.
- **Icons: line-1.5 (thin editorial)** — 1.5px stroke on a 24px grid, Lucide-outline vocabulary as reference (skill icons.csv rows 21 check, 22 check-circle, 28 clock, 32 send, 33 bell, 44 mic, 77 flag, 66 clipboard, 61 file-text — converge with the thin-stroke intent). Constructed to the grid because no skill row carries them: the **loop glyph** (two thin arrows forming an open circle — the handshake cycle), the **commitment seal** (thin check inside a hexagonal seal — the Ta'ahhud mark), and the **evidence-span link glyph** (thin quotation-frame). No sparkle glyphs anywhere; the assist affordance is a thin lattice mark with a written suggestion label (ai-native-patterns §1: no magic affordances).
- **Motion: minimal** (motion-language §1): opacity-only transitions ≤120ms; position changes are instant with a crossfade; route changes crossfade ≤180ms; the register's zone-chip changes are 120ms opacity steps always paired with a text delta (motion never carries information alone — a11y-baseline §4). Success moments: state chip + polite announcement. **The single signature micro-interaction (T3: exactly one): "The Ta'ahhud Settle"** — on the owner's confirmation, the confirmation chip crossfades (opacity-only, ≤120ms) from outlined-slate to filled-green with the commitment seal, while the owner's name and the timestamp settle into the text row beneath. It is the product's one moment of weight: a promise becoming a record. Reduced-motion: the crossfade collapses to an instant state change + the same polite announcement — identical perceivability by construction.
- Errors arrive (opacity step + assertive announcement), never shake, never bounce; nothing celebrates routine saves (motion-language §6).
