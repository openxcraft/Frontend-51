# 00 — Brief: translation-review-hub

Family: content_tools · Tier: 2 · Roster status: researched proposal, pending owner confirmation · Seed: none supplied.

## What it is

A bilingual review workspace for localization teams working across Arabic and English. Content that has *already been translated* — by an agency, an in-house translator, a machine-translation pipeline the team runs elsewhere, or any mixture — arrives at the hub as a review job: one or more documents, each split into aligned segment pairs (source segment ↔ target segment). The reviewer works through the pairs in a side-by-side workspace where the source pane and the target pane each render at their own script direction (an English source sits LTR beside an Arabic target running RTL — the pane-direction contract, 05/09), and every segment carries the deterministic QA state computed for it: terminology violations against the workspace glossary, length-fit warnings against the segment's declared character budget, and consistency findings across the job.

The product's checks are rules, not judgments — declared **non-AI** (ai-native-patterns §1): terminology enforcement is normalized term matching (Arabic normalization per rtl-rules §4: alef/hamza variants, taa marbuta/heh, yaa/alif maqsura, tashkeel stripping), length-fit is arithmetic on declared limits, and consistency is same-source/different-target and same-target-term/different-source comparison across segment pairs. The same input state always produces the same findings — which is exactly what a review artifact requires (Smartling's own LQA framing: evaluation "against a defined schema of objective errors", 01). Reviewers make the human decisions the machinery cannot: approve, reject, or query a segment; edit a target in place and watch the findings recompute; override a critical violation with a recorded reason; and carry the job to sign-off, a gate that refuses to pass while critical violations stand unresolved and unexplained. Every consequential action lands in the activity log (P17), and the deliverable is an export package — bilingual review table, QA report, and the termbase as reviewed — never a silent channel write.

The gap this occupies is narrow and real: QA checkers (Xbench/Verifika class) run inside desktop CAT workflows built for translators, not for the in-country reviewer layer; TMS platforms bundle review into full delivery pipelines the team may not run. The regional wedge is sharper: "Arabic" is simultaneously a locale decision, a script-direction decision, and a layout decision (Smartling, 01), Arabic terminology consistency is a named source of rework (RWS, 01), and no published ar↔en expansion table exists to lean on — so length budgets must be declared per segment and enforced honestly rather than assumed from European-language expansion folklore (W3C's IBM table covers English→European only, 01). A focused ar/en review surface with terminology enforcement and length-fit warnings tuned for that pair is absent from the category (01 positioning gaps), and the adjacency boundary with the creation-time bilingual transform owned by arabic-copy-studio is recorded in both products' 12-open-questions (LOOP-3).

## Buyer

Localization teams (2–30 seats) at MENA-market brands, e-commerce and fintech product groups, publishers, and agencies delivering ar↔en work: the localization lead who owns release quality is the economic buyer; the senior Arabic reviewer/linguist is the daily user; the English source-content owner answers queries from inside the same job. Secondary: small LSP delivery teams that need a reviewer-facing workspace their translators' CAT seats don't cover. This is a team tool — per-seat with a reviewer-first model (12 Q-3) — not a translator CAT replacement (LOOP-10: no MT engine, no translator productivity tooling).

## Surface

Web application, desktop-first (≥1280px primary; responsive to 360px in read/report modes — segment *editing* is desktop/tablet). Zones: review-jobs home (list, filters, saved views); review workspace — the core surface — as a three-region layout: segment navigator (virtualized pair list with decision/violation state) on the inline-start edge, the side-by-side pair view (source pane + target pane, per-pane direction) center, and the findings rail (term violations, length warnings, consistency notes for the focused segment) on the inline-end edge; document overview with QA report; findings console across a whole document; glossary manager (list + term editor); sign-off & export; jobs center for imports/scans/exports; settings. ⌘K command palette with bilingual normalized search (P05, T2 mandate). No mobile app; no browser extension; no public API at v1.

## Unique feature

Side-by-side ar/en review with **terminology enforcement and length-fit warnings** — defensible on four grounds (evidence in 01): (1) the pane-direction contract is structural, not cosmetic — opposite-direction panes that stay aligned segment-to-segment, with dual-pane focus synchronization (09), which single-direction review tools structurally mishandle (RTL corruption evidence, 01); (2) terminology enforcement with critical-vs-advisory severity is the exact convention QA-checker loyalists cite ("load a glossary, define which terms are critical versus advisory, run the check", 01) — here it is enforced live during review, with every violation resolvable only by edit, recorded override, or marked false-positive; (3) length-fit warnings per declared character budget, with severity zones and a meter that reads in both directions of the pair (en→ar and ar→en jobs both first-class) — the practice TMSs productize as per-string limits (Smartling, 01) and open-source platforms still request as an idea (Weblate discussion, 01), with no ar↔en expansion folklore to hide behind; (4) the sign-off gate: a job cannot pass review with unresolved critical findings — the governance artifact the MQM/DQF world scores after the fact, produced *at* the moment of decision (01).

## Exclusions (LOOP-10)

- No machine-translation engine of its own — the product reviews translations; it does not produce them. An optional "machine-translation assist channel" is declared as an abstract, contract-compatible integration need (08 N4) with its v1 logic explicitly out of scope; the manual alternative is the reviewer's own translation typed into the target pane.
- No interpreter booking, no vendor/translator marketplace, no agency routing.
- No CMS connectors at v1 — content intake is an abstract capability ("content intake source") with paste and file upload as the always-available manual path (LOOP-5).
- No translation-memory authoring/leveraging, no TM Concordance, no translator CAT productivity features (segment-fill, predictive typing) — the review decision surface is the product.
- No publishing/delivery of translated content to any destination — export package is the handoff (abstract "review export channel", 08 N2).
- No LLM anywhere in the check pipeline (declared non-AI); no style-guide authoring CMS (governance belongs to brand-voice-guardian's family); no creation-time bilingual transform (arabic-copy-studio's family, LOOP-3 mirror recorded in 12).

## Success signals (definition of done vs Mock Adapter)

A localization team can: create a review job (en→ar and ar→en both exercisable); import a document by paste (zero credentials, LOOP-5); run the deterministic QA scan and read the findings console; resolve a critical term violation by editing the target and watch the finding close; acknowledge a length warning with a recorded reason; query one segment to the source owner; manage glossary terms (add, edit, deprecate); bulk-approve a filtered clean set; hit the sign-off gate and be refused with a named blocker, then pass it; export the review package and retrieve the artifact before expiry — all in the first session, on the Mock Adapter, with zero provider-specific knowledge anywhere in the UI and the full flow completing with every abstract capability unbound.
