# 03 — UX Flows: cod-order-confirmation

SME-C pass · Critical paths with edge cases, failure modes, and recovery. Every path is the justification source for adapter operations in 07a/07b; the bidirectional traceability tables at the end prove zero orphans in BOTH directions (flagship obligation). Agent flows are specified on the console surface (≥1280px, keyboard-first) with the on-call mobile view (≥360px) as the away-from-desk leg; manager/dispatch/ops flows on the console. The buyer never touches this product's UI — buyer touchpoints are authored content delivered through abstract channels (08) whose structured replies arrive as events; the console is the merchant's side of every conversation below.

## CP-1 — Morning batch: order intake, triage, and the live queue (agent + manager; console + on-call)

1. **Entry**: getSession routes by role — agent → QUEUE (S2, default), manager → QUEUE with the day's outcomes snapshot rail, dispatch → MANIFESTS (S7), ops manager → QUEUE (policy badge in header). First-run lands on the P22 checklist with four persona entry paths (02).
2. **Order intake (abstract source, LOOP-5 primary = paste)**: the merchant imports the day's COD drafts by paste — `importOrders` (CSV/TSV with column mapping preview; rows: orderRef, buyer name, phone, city/zone, district, value, items note, language). This is a **Job** (async-contract §2): determinate per-row progress ("استيراد الصف 4 من 60" / "importing row 4 of 60"), `awaiting-input` on ambiguous rows (unknown zone code → row-level choice, never a silent drop), partial-results policy per async-contract §4. A bound order-source channel (08 N1) is the abstract upgrade; the paste path stays primary at v1.
3. **Triage at import**: every imported order is scored by the risk engine (07c §2 — the deterministic scorecard runs at seed/import time so the queue never renders an unscored row), and the ladder **auto-starts** for orders whose band and hold-rules permit (LadderPolicy.autoStart: `all` | `below-high-risk` | `none`; seeded default `below-high-risk`). Orders over the value cap import straight to `held-review` (CP-4.2). Blocked buyers' orders import to `held-review` with the blocklist reason surfaced.
4. **The queue renders** (listCodOrders, cursor-paginated ≤50): dense A-radius rows — orderRef (bidi-isolated Latin token), buyer name, city + zone, value (workspace currency, Western numerals), **RiskRail band chip** (low/medium/high — text+icon, never color-only), **Ladder Trail state** (rung count + active rung state + time-to-next-attempt countdown), aging badge (time since import), and the agreement state column (stamped window or "—"). Sorting default: **time-to-next-attempt asc, then risk desc** — the queue IS the work order.
5. **Filtering**: filter chips + saved views (P08) — band, ladder state, agreement state, zone, value band, aging; every active filter declares its predicate accessibly; filtered-empty offers reset + names what exists outside the filter (P01). Lists above 200 rows virtualize with focus preservation (P19).
6. **Row → drawer** (Enter): the working context opens without navigation (CP-2). On the on-call mobile view the same data renders as stacked cards with the drawer as a bottom sheet.

**Edge cases**: duplicate orderRef in the paste → job parks `awaiting-input` with both rows shown, explicit keep/skip per row (never silent dedupe); buyer phone already in directory → order links to the existing buyer record (history surfaces in the drawer — CP-2.2); order with missing zone → triages with address-quality component at minimum and a "zone unmatched" flag the agent resolves in the drawer; mixed-script names → bidi isolation on render (rtl-rules §2).
**Failure modes**: importOrders VALIDATION (malformed paste) → row-linked errors quoting the offending row; RATE_LIMIT (import frequency cap) → count + reset window; NETWORK mid-import → job reconcile (idempotency key; async-contract §5); order-source channel credential failure → surface degrades to paste-only with the credential state named (credential-contract §3; 11 copy).
**Recovery**: imports are resumable jobs (retryJob scoped to failed rows); nothing is committed per-row until the review step confirms the batch.

## CP-2 — Working the ladder: attempts, cooldowns, and the call leg (agent; console keyboard-first + on-call)

1. **Queue navigation**: j/k (or ↑/↓) move rows with 2.4.13-strength focus; the drawer expands in place (Enter) — buyer card, risk rail with component drill, the Ladder Trail, prior responses verbatim, and the contextual action row. The drawer never navigates away: queue context (aging, countdowns) is decision information (04 IA decision).
2. **Buyer card** (getBuyer via the drawer's data need): completed / refused / unreachable counts over the trailing window, tenure, language preference, blocklist state — Hessa's "do I know this number?" answer in one glance.
3. **The Ladder Trail renders the state machine** (original interaction #1, full spec 13 §B1): rungs left→right (RTL: right→left) for attempt 1 (rich message), 2 (SMS-class text), 3 (voice/IVR), 4 (agent call); each rung shows its state (queued → sending → sent → delivered → read → responded; or failed / skipped), sent timestamp, and the buyer's response verbatim when it lands. The **cooldown arc** on the active rung counts down to the next eligible send time (quiet-hours aware — the engine computes it; the trail visualizes, never guesses).
4. **Engine-driven dispatch**: attempts fire automatically at policy cadences (07c §2: attempt 1 at T+0 or next quiet-hours-exit; cooldown 4h; attempt 2; cooldown 16h quiet-aware; attempt 3; expiry at 48h). The agent's queue shows **time-to-next-attempt**, and the trail stamps each firing. The agent never babysits sending — she handles exceptions and the human rung.
5. **Reschedule an attempt** (`rescheduleAttempt`): defer ("call after العصر" → +90m) or advance ("send now, cutoff at 15:00" → immediate). The engine validates against quiet hours and the ladder's expiry; the trail re-aims the cooldown arc; defers are visible facts on the trail, never hidden state.
6. **The voice rung / call leg**: when rung 3 activates (or the agent takes the human rung early), the **Call Leg Sheet** renders the bilingual call script (template-driven), the buyer history card, and prior responses side-by-side (06). The agent works the call and records the outcome: `logManualContact` with outcome `confirmed-with-window` | `confirmed-no-window` | `cancelled` | `reschedule-request` | `unreachable` | `wrong-number`, plus a bounded note (≤140 chars, bidi-isolated).
7. **Structured response capture**: channel-mediated replies (button tap, keypad digit, SMS reply keyword) arrive as events (subscribeOrderEvents) and stamp the trail engine-side; when the agent captures a response by phone, she records it through the same typed surface — `recordBuyerResponse` with response `confirm` | `cancel` | `reschedule-request` | `wrong-number` and, on confirm, the window choice (CP-3). One grammar for every source of truth.
8. **Live queue behavior**: events patch rows in place (rank-of-work order reshuffles only off-viewport or on scroll-idle — never under the cursor); response landings announce politely on the focused row only (09); nothing toasts per event (P21 discipline).

**Edge cases**: buyer replies to attempt 1 with a window choice while the agent is mid-call on the same order → first-write wins, second capture surfaces CONFLICT with both payloads shown (P10-style compare); attempt fails at channel level (delivery failure, template rejected) → rung state `failed` with the channel error class named, engine auto-falls-through to next rung per policy (failover ladder), agent sees the failure reason verbatim; buyer answers in dialect free text on the message channel → response recorded verbatim, classification is the agent's judgment call at capture (no silent AI classification — conditionally-AI declaration scoped to risk enrichment only); order cancelled at the storefront mid-ladder (source refresh) → order resolves `cancelled-upstream`, ladder halts, agent sees the reason; the same buyer has two orders in the queue → ladder runs per order; the drawer surfaces the sibling order to avoid double-calling.
**Failure modes**: rescheduleAttempt VALIDATION (time inside quiet hours / past expiry) → the failing rule named inline with the next eligible time offered; logManualContact PERMISSION (agent suspended) → lock state with restore path; recordBuyerResponse CONFLICT (order already resolved) → both states shown, no dead click; RATE_LIMIT (manual-contact logging spam guard) → cooldown copy; NETWORK → queued writes (P20) reconcile against authoritative order state.
**Recovery**: every ladder state is replayable from the ledger (listActivity); the trail's history is immutable — corrections are new entries, never edits (P17 discipline).

## CP-3 — The Agreement Moment: window selection and the stamp (agent sheet + channel quick replies; the flow the product is named for)

1. **Trigger**: a confirm response arrives (channel button, keypad menu, agent capture, or manual call outcome `confirmed-with-window`). The order moves to `awaiting-agreement` (or straight to `confirmed` when the channel reply already carried a window choice — quick-reply buttons encode window ids, so the buyer's single tap IS the agreement).
2. **The agreement sheet opens** (W from the drawer, or auto-opened on the channel-reply event): eligible windows via `proposeWindowsForOrder` — zone-matched, capacity remaining > 0, start ≥ now + lead time (policy, seeded 6h), within the horizon (seeded 7 days). Windows render as day-grouped chips with day-part labels in both locales and remaining capacity ("صباحاً 9–12 · متبقٍ 12" / "Morning 9–12 · 12 left") — Western numerals everywhere (ledger numeral policy).
3. **Channel mirror**: the same eligible set was encoded in the message template's quick replies (previewMessage shows the buyer view before send — 06 MessagePreviewSheet); the voice rung's keypad menu offers the same windows by number. One catalog, three rungs — the agreement never depends on which channel answered.
4. **Selection**: agent taps/keys the window (arrow navigation, Enter to commit; on-call path identical). `recordBuyerResponse` with `confirm` + windowId writes the **WindowAgreement** (attempt id, channel kind, timestamp, response verbatim, window id) — ledger-grade evidence by construction (07a).
5. **The Agreement Stamp** (signature moment, full choreography 13 §B2): the selected window chip presses into the order's agreement slot with a single crisp stamp (≤140ms, scale 1.0→0.97→1.0, 1px border.interactive edge flash at land — NO overshoot, crisp personality), leaving the stamped chip carrying window + evidence glyph. The risk score recomputes live (agreement improves the latency and engagement components — 07c §2) and the RiskRail settles to its new band with the delta named.
6. **Capacity effects**: the window's remaining count decrements on the sheet, the queue's agreement column, and the window catalog (S9) in the same event — one source of truth (07a denormalized consistently).
7. **Confirmed-without-window**: manual-call confirms that could not pick a window (`confirmed-no-window`) enter `confirmed` with an open `agreement: null`; the queue shows the "window owed" state (text+icon) and CP-5 excludes nothing — manifest rows carry the flag and dispatch resolves it at packing (Munira's rule: flagged boxes ship on the date band, not a window promise).

**Edge cases**: window fills between proposal and commit → CONFLICT-style re-render with the next eligible window focused, the agent's selection preserved (no dead click); buyer requests a custom window outside the catalog → recorded as `reschedule-request` with the requested time in the note; catalog window for the buyer's zone has zero capacity for 3 days → the sheet surfaces the neighboring-zone option explicitly (agent judgment, never silent substitution); buyer language is en while the workspace is ar → the sheet's labels render per the buyer's locale for the message preview, the console stays in the agent's locale (two locales, two surfaces, one record).
**Failure modes**: recordBuyerResponse VALIDATION (window not eligible for zone / capacity zero) → the failing rule named with the eligible set re-proposed; proposeWindowsForOrder NOT_FOUND (zone has no catalog) → empty-with-reason state linking to the window catalog (P01 no-data-after-activity shape); NETWORK → the capture queues (P20) and reconciles — an agreement never double-writes (idempotency key).
**Recovery**: agreements are immutable; a changed mind is a NEW response (`reschedule-request`) producing a new agreement — the trail keeps both (dispute-grade history, 02 Salem).

## CP-4 — Exceptions, auto-cancel, holds, and the dispute ledger (manager + agent)

1. **Ladder exhaustion → auto-cancel**: at expiry (seeded 48h) with no confirm, the engine resolves the order `auto-cancelled`, sends the final-notice template, updates buyer history (`unreachable` outcome), and emits a digest notification. Auto-cancel is POLICY (LadderPolicy.autoCancelOnExhaustion, seeded true) — never a surprise: the trail showed the expiry countdown from minute one.
2. **Value-cap hold**: imported orders with value > RiskPolicy.valueCap land in `held-review` (S6). The manager reviews the hold card (order facts, buyer history, cap math rendered — "القيمة 640 ريال، السقف 500" / "Value 640, cap 500"), then `setOrderHold(false, reason)` to release into the ladder, or `cancelCodOrder` with rationale. High-band risk policy can also route to hold (policy flag, seeded on for `high` band × value > 0.5×cap).
3. **Wrong-number responses**: buyer response `wrong-number` flags the phone record; the agent suggests blocklist, the manager executes `setBuyerStatus(blocked, reason)` — the directory shows blocked buyers with reasons and restore paths (never a silent dead list).
4. **Buyer cancellations**: `cancel` response → order `buyer-cancelled`, template acknowledgment, history updated (`cancelled` outcome — distinct from `unreachable` in the scorecard, 07c §2).
5. **The dispute test (00 success signal 4)**: order → LEDGER tab → the full chain in two clicks: every attempt (kind, state, timestamps), every response verbatim, the stamped agreement with its evidence glyph, policy versions in force, actor names. `exportConfirmationLedger` (period- or order-scoped) produces the evidence artifact as a Job with an expiry window (async-contract §2) — Salem's dispute ends in a document, not a memory.
6. **Post-handoff outcomes**: the abstract courier channel reports outcome events (delivered / refused / returned / lost) that update buyer history and the outcomes panel — the product RECORDS outcomes (buyer-history inputs for tomorrow's risk scores); re-attempt/NDR workflow itself is out of v1 scope (LOOP-10, honest boundary in 11 copy).

**Edge cases**: auto-cancel fires while the agent is mid-call on the order → call outcome captures as `unreachable` against the resolved order, no phantom re-open (CONFLICT copy states the resolution); manager releases a hold after expiry already passed → ladder resumes at the next eligible attempt with the remaining runway recomputed; dispute export for a period with zero events → explicit empty with scope explained (P01); buyer disputes the WINDOW (claims Thursday, ledger says Sunday) → the trail's response verbatim is the arbitration surface; two managers release/cancel the same hold concurrently → first-write wins, second gets CONFLICT with both payloads.
**Failure modes**: setOrderHold PERMISSION (agent role cannot release value-cap holds) → lock state with request-approval action; cancelCodOrder VALIDATION (order already handed off — sealed manifest) → named boundary: the manifest is sealed, courier notice is out-of-v1 (honest copy, 11); exportConfirmationLedger RATE_LIMIT → window + reset; NETWORK → exports are jobs that reconcile (idempotency).
**Recovery**: holds and cancellations append to the ledger; nothing destructive is silent (P04 ladder applied — cancellation of ONE order is undo-window'd (P03) only before manifest sealing; sealed-manifest cancellations are explicit, named-consequence actions).

## CP-5 — Manifest build, seal, and courier handoff (dispatch; console + paper reality)

1. **Entry**: MANIFESTS (S7): confirmed orders with agreements grouped by delivery date + window; the default draft view is "today + tomorrow, unmanifested". Rows show orderRef, buyer, zone, value, band, agreement window, and the window-owed flag (CP-3.7).
2. **Build**: `createHandoffManifest` from explicit selection (P07 bulk-select with keyboard range) or a by-filter batch (date + zone) — the manifest draft assembles with a review rollup: count, total value, window/date mix, risk-band rollup, and exception list (agreement-owed flags named; nothing without a `confirmed` state can enter — the engine excludes and the UI explains, never silently drops).
3. **Review**: the rollup is the trust gate for Munira — the count is named, the mix is visible, sealed means sealed ("ختم 41 طلباً — 5 نوافذ، بقيمة 8,240 ريال" / "Sealing 41 orders — 5 windows, value 8,240 SAR" — the 11 §D6 rollup template composed).
4. **Seal**: `sealHandoffManifest` locks the batch (immutable — 07a state machine). Late confirmations route to the NEXT manifest; the surface shows the next-manifest path explicitly (no silent edits, no unsealing).
5. **Export/handoff**: `exportManifest` → Job → artifact (expiry window declared). The abstract courier handoff channel (08 N4) is the binding-time upgrade; the manual path — download and print the driver sheet — is a first-class primary output (Munira's reality: "the driver takes paper").
6. **Post-seal corrections**: an order cancelled after sealing is flagged on the manifest view with the cancellation entry linked (courier notice itself is out-of-v1 scope — recorded boundary, 11 copy states it plainly).

**Edge cases**: attempt to include an agreement-owed order → allowed with the flag carried (CP-3.7 rule), the rollup names the count; manifest build over the row cap (500) → Job-shaped with progressive assembly; buyer changes window after sealing → new agreement recorded, the manifest row keeps the SEALED window with a divergence note (evidence over convenience — the ledger explains the gap); export job fails midway → partial-results policy with retry scoped to the artifact build; printing without a bound channel → the download path is the default, not a degraded mode.
**Failure modes**: createHandoffManifest VALIDATION (zero confirmed orders in selection) → named reason; sealHandoffManifest CONFLICT (manifest changed since review — a row resolved underneath) → re-review with the diff highlighted; exportManifest PERMISSION (dispatch+manager roles only) → lock state; NETWORK → job reconcile.
**Recovery**: drafts are editable; sealed manifests are immutable BY DESIGN — recovery is always the next manifest, never an edit (the trust boundary Munira buys).

## CP-6 — Policy spine, people, buyers, templates + the resilience walkthrough (manager/ops; documented and tested)

1. **Policy center** (S9): ladder policy — attempt sequence (kinds + order), cooldowns, quiet hours (per site, default 21:00–08:00 buyer-local), expiry hours, auto-cancel toggle, auto-start mode; risk policy — component weights (must sum to 1), value cap, band thresholds, hold rules. Both versioned; both render as the SAME sheets agents see (inspectability, 02 Fahad).
2. **Simulation gate**: `simulateRiskPolicy` runs the proposed weights over currently open orders and returns the before/after band rollup + the highest-jumping sample orders; `updateRiskPolicy` requires `simulationConfirmed: true` (contract-enforced, 07b rule 4 — the gate is not UI theater). `updateLadderPolicy` carries a quiet-hours preview (next-24h send calendar under the proposed hours) — policy changes never surprise the queue (02 Salem).
3. **Window catalog**: `listDeliveryWindows` (zone/date/grid with capacity); `upsertDeliveryWindow` (zone, date, start, end, capacity) — day view shows remaining vs total; overbooking attempts VALIDATION with the count named.
4. **Templates studio** (S8): `listMessageTemplates` (per rung: rich message, SMS text, voice script, keypad menu; plus final-notice and cancel-ack templates); `upsertMessageTemplate` (bilingual AR/EN bodies with parameter slots; versioned); `previewMessage` renders the buyer-view for a chosen order — bidi isolation visible, per-locale direction, parameter values filled (06 MessagePreviewSheet). Templates are DATA the engine composes (07a) — no AI writes buyer messages (conditionally-AI declaration).
5. **People** (S9 tab): `listUsers` / `inviteUser` / `updateUser` — three structural roles (agent / manager / dispatch); role changes are ledger entries.
6. **Buyers directory** (S10): `listBuyers` (search with Arabic normalization — rtl-rules §4), `getBuyer` (history trail), `setBuyerStatus` (block/restore with reason — manager+ only).
7. **Notification ladder** (P21, S12): instant tier = agreement stamped (agent whose queue it is), hold awaiting decision (manager); digest tier = ladder transitions batched, auto-cancels, capacity warnings (window ≥80% full), template/policy publishes. `listNotifications` + `markNotificationsSeen`; tier control per class per user; the product never multiplies toasts (02 Hessa).
8. **Jobs center** (S11): `getJob` / `retryJob` / `cancelJob` — imports, manifest exports, ledger exports; retry scoped to failed rows/items only (async-contract §4).
9. **Live events**: `subscribeOrderEvents` drives queue row patches, trail stamps, capacity decrements; the mock replays a fixed event script deterministically (07c §4).
10. **Offline discipline (P20)**: manual-contact logs and response captures queue locally with per-item state; on reconnect they reconcile against authoritative order state — a queued capture that reaches a resolved order discards with an honest notice (never a phantom write).
11. **Full-day walkthrough (00 §success signal 2, release-test fixture)**: 09:30 paste-import 60 orders (56 imported — 2 failed rows quoted, 2 awaiting-input rows resolved as skips; the seeded import-job shape, 07c §1) → triage bands (12 low / 37 medium / 7 high; the 3 over-cap holds sit inside the high band — weak-history buyers placing over-cap orders, exactly the pattern the cap exists for) → ladder auto-starts below-high (49 orders) → 11:00 attempt-1 responses land (9 confirms with windows, 4 cancels, 36 quiet) → cooldown arcs → 14:00 attempt-2 SMS leg (20 keyword confirms) → 14:25 voice rung for the stubborn 12 + agent call leg on 4 → 14:40 agreement stamps (2 final confirms — the day closes at 31) → 14:50 manifest build (31 confirmed) → seal (count review) → export/print → 15:00 cutoff clean. Ledger check: 31 confirmed + 4 cancelled + 14 unresolved + 3 held + 4 high-not-started = 56 imported. Then the degradation re-run: every channel unbound — manual calls logged, paper manifest printed, bands deterministic — same day completes. Total: 6 screens, zero stalls, replayed twice byte-identical (07c §5).

## Failure-mode → error-class mapping (feeds 07b/11)

| UX failure | Error class | User-facing surface |
|---|---|---|
| Paste/import row malformed; window/zone invalid; response payload invalid; template parameters missing; weights ≠ 1; reschedule inside quiet hours; deny-style actions without required reason fields | ValidationError | field/row/rule-linked inline error naming the failed rule |
| Order/manifest/buyer/window/template/job id absent or resolved (expired order, sealed manifest, resolved response) | NotFoundError | safe-state + list re-sync + next action |
| Role scope violation (agent on policy/blocklist/manifest-seal surfaces; dispatch on policy; suspended user) | PermissionError | lock state with request-access action |
| Concurrent writes (double response capture, manifest changed at seal, hold decided twice, buyer status raced) | ConflictError | both-states compare, explicit re-decide |
| Import frequency, manual-log spam guard, export frequency, simulation spam | RateLimitError | count + window + reset copy (P14-style transparency) |
| Offline / transport drop mid-write / channel delivery failure surfaced to UI | NetworkError | P20 queue with per-item state + honest reconciliation |
| Anything else | UnknownError | correlation-id copy (copy-voice §1.4) |
