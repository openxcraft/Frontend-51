# 03 — UX Flows: kyc-onboarding-flow

SME-C pass · Critical paths with edge cases, failure modes, and recovery. Every path is the justification source for adapter operations in 07a/07b; the bidirectional traceability tables at the end prove zero orphans in BOTH directions (flagship obligation). Applicant paths (CP-1…CP-4) run on the applicant shell (≥360px, touch, RTL-first, one question per screen); reviewer and ops paths (CP-5, CP-6) run on the review console (≥1024px, keyboard-first). The two shells never render each other's surfaces: applicants never see queue mechanics, reviewers never see step authoring, admins own the program (04 role routing).

## CP-1 — Applicant entry: the two doors, session discipline, and the resume contract (applicant shell)

1. **Entry (A1)**: the applicant arrives from the fintech's product (deep link carrying the workspace's program code) or from a resume link. Two doors render, never a marketing hero: **ابدأ طلباً جديداً** / "Start a new application" and — when a resumable application exists for this contact — **استأنف طلبك** / "Resume your application" with the fact line ("توقفت عند خطوة المستند — قبل 3 أيام" / "You stopped at the document step — 3 days ago"). Locale pick (ar/en) persists with the application. First-run applicants see the resume contract stated up front: answers save as you go; a resume link works for 30 days; data-use is stated plainly (02 Amal's data-loss fear answered before step one — P22 discipline, no tours).
2. **Start**: `startApplication` (programCode, applicantLocale, contactChannel) creates the Application (state `in-progress`), the step instances from the FlowProgram version in force, the resume token with its declared window, and routes to the first incomplete step. The Progress Spine (the flow's signature navigation object, 13 §B1) renders the step sequence immediately — completion state is visible from the first screen, never hidden behind a progress bar that appears later.
3. **Resume**: `resumeApplication` (resumeToken) resolves the Application, validates the resume window (30 days from last activity, seeded policy), and returns the applicant to the EXACT last step with prior step answers rendered as **recalled** (P11 marking: "مسترجع من جلستك السابقة" / "Recalled from your previous session" — a visible chip on pre-filled values, never silent pre-fill). A resumed application never restarts completed steps; rework-flagged steps render their needs-attention state (CP-5.5).
4. **Session discipline (a11y-baseline §7 fintech overlay — contract-enforced, not optional)**: idle timeout (seeded 20 minutes) warns at 2 minutes remaining with an **assertive live-region announcement** and a visible countdown ribbon offering **مد الجلسة** / "Extend session" (`extendSession` → new deadline, announced politely) and "save and exit" (answers already autosaved; the ribbon states it). Timeout itself never destroys data — it ends the session; the application persists as a durable draft (07a lifecycle). Absolute session cap (seeded 60 minutes) is stated in the ribbon from session start.
5. **Nudge path (ops-initiated resume)**: when an application idles past a policy threshold (seeded 48h), the console's nudge action (`sendResumeLink`) delivers the resume link through the abstract message channel (08 N3) using the versioned bilingual template; the manual alternative is copy-the-link (console shows a copyable link + QR — LOOP-5). The nudge is recorded in the ledger as an activity entry (P17).
6. **Console-side entry (for completeness)**: `getSession` routes by role — reviewer → QUEUE (R1, default), admin → QUEUE with the program badge (R3 one keystroke away). First-run lands on the P22 checklist with four persona entry paths (02).

**Edge cases**: resume token expired (window elapsed) → the door renders the expired state with the data-retention line and a restart action that cites policy, never a dead 404; token already used from another device mid-session → CONFLICT rendered as the two-session fact with a choose-continue action (never silent takeover); applicant locale differs from template locale → notices render in the applicant's locale; deep link carries an unknown program code → NOT_FOUND safe state with the workspace contact path; contact channel returns a hard bounce → the nudge records the failure state honestly (11 §G).
**Failure modes**: startApplication VALIDATION (malformed contact identifier) → field-linked error; resumeApplication NOT_FOUND (token unknown/expired) → expired-door state + restart path; extendSession CONFLICT (session already ended) → the ended state with resume link offer; sendResumeLink RATE_LIMIT (nudge spam guard, seeded 3 per application per 24h) → count + reset window copy; NETWORK → applicant shell queues writes locally (P20) and reconciles against authoritative application state.
**Recovery**: every applicant action is autosaved (CP-2.4); recovery is always resume, never re-entry; a crashed session re-enters through the same door with the same token semantics.

## CP-2 — The identity steps: one question at a time, with autosave and recall (applicant shell)

1. **Step surface (A2)**: each step is one screen, one decision (01 §4.4: the one-question-per-screen pattern) — identity fields grouped into micro-steps (name group, national identifier group, contact group) per the FlowProgram's step definitions. Labels persist above fields (a11y-baseline §5); required is programmatic; autocomplete tokens declared for personal-data fields (name, email, tel, address-level tokens).
2. **Program-driven**: the FlowProgram (R3-authored, versioned) defines step order, field sets per step, validation rules, and branch conditions (e.g., document-type step branches the document-capture requirements). In-flight applications continue under the program version they started (07a versioning rule); program changes affect NEW applications only — the console states this at publish (CP-6.2).
3. **Answer state**: `saveStepDraft` autosaves on field blur and step change (P10): the save indicator is a persistent calm surface cycling saving → saved (fades after 3s) → conflict → offline-queued; drafts are visible facts, never inferred. `getApplication` hydrates the resumed step bundle (answers + validation state + recall chips).
4. **Recall across steps (P11/WCAG 3.3.7)**: later steps pre-fill values the applicant already gave (contact → notification preferences); every pre-filled value renders with the recalled chip; the applicant can change any recalled value in place (changes propagate forward with a visible note, never silently).
5. **Validation**: on-blur-or-submit per a11y-baseline §5; errors are field-linked with inline messages in both locales; submit-step validation (`submitStep`) checks step independence — each step independently valid before advancing (P09); the failing rule is named in the message (never "invalid input").
6. **Step completion**: submitting a step folds it into the Progress Spine (the fold choreography, 05 motion signature) and advances to the next incomplete step; completed steps remain navigable backward for amendment until submission (CP-4) — amendment marks the step amended in the timeline (ledger entry).

**Edge cases**: Arabic name entered with English keyboard numerals in the identifier field → script-normalized validation with the expected format shown; applicant changes a previously-submitted step after capture steps completed → downstream invalidation is NAMED (which captures now need retaking), never silent; mixed-script answers (Latin employer name inside Arabic fields) → bidi isolation on render (rtl-rules §2); offline mid-step → P20 queued writes with per-field state.
**Failure modes**: saveStepDraft NETWORK → queued locally, indicator shows offline-queued, reconciliation on reconnect discards nothing that can be legally kept and surfaces CONFLICT where the authoritative state moved; submitStep VALIDATION → the failing rule named, first error focused; submitStep CONFLICT (step already superseded by a rework request) → both states shown; RATE_LIMIT (autosave flood guard on rapid field churn) → coalesced silently server-side, surfaced only in the indicator's tooltip — the applicant is never scolded for typing.
**Recovery**: drafts are the unit of recovery; the step timeline is immutable (amendments append); no path exists that discards a valid draft.

## CP-3 — The document step: coached capture with deterministic gates (applicant shell; the flagship mechanic)

1. **Step entry (A3)**: the document step states what it needs and why, per document type (workspace-configured data: type catalog, sides required, orientation): "سنطلب تصوير وجه البطاقة الآن — للتحقق من صلاحيتها" / "We'll ask you to photograph the front of your card now — to verify its validity." The data-use line and the manual-upload alternative path ("ليست لديك كاميرا جيدة؟ ارفع صورة موجودة" / "No good camera? Upload an existing photo") are stated BEFORE the camera opens — the alternative is a first-class path (a11y-baseline §7), never a buried settings link.
2. **The Capture Coach (original interaction #2, full spec 13 §B2)**: on camera start, the surface enters the capture viewport — the one dark-navy surface in the product (05) — with the frame guide (the document-outline overlay sized to the required type), the live quality checklist (the five deterministic gates: framing, glare, blur, alignment, edge completeness — each with its bilingual label and current pass/fail state), and the guidance line. Screen-reader guidance is contract copy: "امسك المستند مسطحاً، والأركان الأربعة داخل الإطار" / "Hold the document flat, all four corners inside the frame" — announced on camera start and on gate transitions (a11y-baseline §7 verbatim class).
3. **Real-time frame evaluation**: `evaluateCaptureFrame` (the declared conditionally-AI surface) runs during capture on frame metrics: with the assist capability BOUND it returns enriched hints ("حرّك المستند قليلاً بعيداً عن الضوء — وهج في الزاوية العلوية" / "Move the document slightly away from the light — glare in the top corner"); with the capability UNBOUND it returns the deterministic gate states with the static checklist guidance for any failing gate — identical surface, degraded richness, engine provenance displayed ("إرشاد وفق القواعد" / "rule-based guidance" vs "إرشاد مساعد" / "assisted guidance" — 11 §D2). The evaluation loop never blocks the shutter: capture is always available; gates ADVISE and the submit path enforces (below).
4. **Gate states render as a live checklist**: each gate row shows label + state (pass/fail) as text+icon — never color alone; the failing gate's fix instruction is the row's sub-line (11 §D2). When all gates pass simultaneously, the coach announces readiness and enables the primary capture action prominently ("جاهز — التقط الآن" / "Ready — capture now").
5. **Capture submission**: the applicant captures (or uploads via the alternative path — the upload runs the same `submitCapture` pipeline with the same gates evaluated post-hoc on the file). `submitCapture` evaluates the five deterministic gates exactly (07c §2.1) and writes the CaptureRecord with its QualityReport: pass → the capture folds into the step's evidence slot; fail → the failing gates are NAMED with values and thresholds ("التقاط غير مقبول — وهج يغطي 12% من المستند (الحد 4%)" / "Capture not accepted — glare covers 12% of the document (limit 4%)") and the retake affordance is focused. Retakes are unlimited within policy (seeded 5 per side per session before the suggested-rest nudge — a kindness rule, not a wall).
6. **Multiple sides and types**: multi-side documents (front/back) sequence as sub-steps of the document step; the spine marks the document step's sub-progress. Each side's QualityReport is retained per capture (retakes chain, latest-best selectable — the applicant can submit an earlier frame; the submitted one is the evidence).
7. **Presence step (policy-optional)**: when the FlowProgram includes the presence step (selfie class), it renders AFTER documents with its purpose stated, the alternative path offered (branch/in-person verification through the fintech's own network — abstract, 08), and capture-only semantics: the product records the image for the verification capability to assess; no liveness claim is ever made by the UI (LOOP-10 — liveness analysis is the abstract capability's judgment, rendered as assessment input, CP-5.3).

**Edge cases**: document type not in the workspace catalog (applicant selects "other") → the step branches to the workspace's declared fallback path (usually upload-only with a reviewer flag); glare persists across retakes → after 3 failed retakes the coach suggests the environment fix with a day-part hint ("جرّب مكاناً أقل إضاءةً مباشرة" / "Try a spot with less direct light") and offers the upload path + save-and-resume (the interruption is expected, not punished); camera permission denied → the upload path becomes the step's primary with the choice stated; capture submitted on the wrong side → detected by the step's side validation, named, retake offered; assist capability fails mid-session → the surface degrades to rule-gates + checklist within the same interaction, provenance flips to rule-based, no error wall (08 N2 degradation map).
**Failure modes**: evaluateCaptureFrame RATE_LIMIT (evaluation flood guard) → evaluation pauses with the checklist pinned to last-known state and a stated reason; submitCapture VALIDATION (gate failure) → the named-gate error above; submitCapture PERMISSION (workspace capture policy off for the step) → cannot occur in-flow (program validation at authoring); NETWORK mid-upload → the upload is a resumable job-class write (P20) with progress honesty (async-contract §8 copy); NOT_FOUND (step reworked underneath) → CONFLICT with the rework notice.
**Recovery**: every capture attempt is retained in the retake chain until submission; the retake loop is guidance, not punishment; the upload path is always available and produces identical evidence structure (07a CaptureRecord.source: 'camera' | 'upload').

## CP-4 — Review, attestation, and submission (applicant shell)

1. **Review & submit (A4)**: the summary screen renders the complete application as readable evidence: identity values (with recalled/amended marks), document captures with their quality reports (thumbnailed, inspectable — the applicant sees EXACTLY what the reviewer will see, the trust symmetry), the presence capture if the step ran, and the program's data-use + retention lines.
2. **Attestation (A5 flow moment, a11y-baseline §7 legal-overlay discipline)**: the attestation panel renders the full agreement text (or the structured alternative for long texts) with **focus order preserved across the entire agreement** — the applicant tabs through it end-to-end; the consent control is disabled until the text has been reachable (never a click-wrapped scroll trap); the attested timestamp is captured with the action and announced ("اعتُمد الإقرار الساعة 21:47" / "Attestation recorded at 21:47").
3. **Submission**: `submitApplication` (with the attestation reference) validates the full step chain, freezes the draft into a submitted application (state `submitted`), creates the ReviewTask with its deadline (07c §2.2 SLA classes), emits the submitted-notice template to the applicant, and routes the applicant to the live status page (A5). The fold settles the whole spine to its submitted state (the one ceremony, 05).
4. **Status page (A5)**: submitted → in-review → outcome; needs-attention renders the reviewer's rework request VERBATIM with the exact steps named, the fix instructions, and the resume action ("استأنف وصحّح خطوتين" / "Resume and fix 2 steps"); approved/rejected render the decision notice with reason summary and the dispute path (the fintech's support — out of product, stated honestly).
5. **Rework round-trip**: a rework decision (CP-5.5) moves the application to `needs-attention`, targets specific step ids, and the notice names them; the applicant resumes through the same door (CP-1.3), fixes the flagged steps (flagged state renders first), re-submits — the rework round increments, the ReviewTask's deadline adjusts (07c §2.2), and the return lands in the SAME reviewer's queue flagged round 2 where policy keeps ownership (seeded: ownership retained through round 2).
6. **Withdrawal**: `cancelApplication` (applicant-initiated, with stated consequence: draft data discarded per retention policy, resubmission starts fresh) and admin-initiated cancellation (rationale REQUIRED, ledger entry, applicant notice).

**Edge cases**: attestation text updated by program version mid-flight → in-flight applications attest under their STARTED version (versioning rule), stated in the panel; submit with one failed capture that passed earlier gates re-evaluation → re-evaluated at submit (gates are pure functions of capture data, 07c); simultaneous rework request arriving during review-and-submit → CONFLICT rendered as the needs-attention fact with the fix-first path; withdrawal racing a decision → first-write wins, the loser sees the resolved state with both payloads (P10-style compare).
**Failure modes**: submitApplication VALIDATION (a step regressed) → the regressed step named + navigated; submitApplication CONFLICT (already submitted) → the submitted state shown, no dead click; cancelApplication PERMISSION (already decided) → the decision state shown; NETWORK → submission is idempotent (keyed, 07b rule 2) — a retried submit never double-creates a ReviewTask.
**Recovery**: pre-submission amendments are free (timeline-noted); post-submission corrections are the rework loop's job — the two-phase discipline is the trust boundary (04 IA decision).

## CP-5 — The review console: queue, evidence dossier, decisions (reviewer + admin; console)

1. **Entry & queue (R1)**: `getSession` routes reviewer → QUEUE. `listReviewTasks` (cursor-paginated ≤50) renders dense B-radius rows: applicant name (bidi-isolated), document types, **deadline ribbon** (SLA class + time remaining — text+icon, tabular numerals), rework-round badge, capture-warning count (gates failed at submit re-evaluation), machine-assessment presence glyph (assessment available / absent — provenance-visible), and aging. Sort default: **deadline asc, then aging desc** — the queue IS the work order (mirrors the cod-order-confirmation IA decision; engine-ranked, never human-triaged). Filter chips + saved views (P08): state, SLA class, rework round, document type, program version; filtered-empty offers reset and names what exists outside the filter (P01). Lists >200 rows virtualize with focus preservation (P19).
2. **Assignment**: tasks default to the shared pool; `assignReviewTask` (or self-claim, S key) moves a task to a reviewer's owned queue with a ledger entry; un-assign returns to pool. Month-end crunch behavior: the queue shows pool depth vs owned per reviewer — workload is visible, never gamed.
3. **The Evidence Dossier (original interaction #3, full spec 13 §B3)**: `getReviewTask` opens the dossier IN PLACE (drawer-over-queue — queue context is decision information: deadline, aging; never a route): layer one — the application summary with the step timeline; layer two — document captures (full images, zoomable, with each capture's QualityReport rendered gate-by-gate — the SAME report the applicant's coach produced, the loop closed); layer three — extracted-data panel (fields as typed data from the abstract verification capability when bound: `requestVerificationAssessment` results render with provenance: engine label, version, timestamp, confidence-as-input-never-verdict); layer four — mismatch flags (deterministic cross-checks: document expiry vs today, name-field vs document-field divergence, gate warnings — computed rules, 07c §2.4). Keyboard traversal is layer-then-item; every layer is one tab region (09).
4. **Decision (R2 composer)**: `decideReviewTask` with decision ∈ approve | reject | request-rework | escalate. Reason codes are REQUIRED for reject and request-rework (policy-seeded catalogs, bilingual, versioned — 07a); free-text note bounded (≤280 chars, bidi-isolated). Approve/reject close the task and emit the decision notice (templates, CP-6.5); request-rework targets step ids (checkbox-list of the application's steps, pre-checked to the mismatch-flagged ones) and round-trips per CP-4.5; escalate re-queues with SLA class `urgent` and a stated reason (senior/admin queue). Consequence-naming copy throughout (P04): "رفض الطلب — سيُبلَّغ مقدّمه بالأسباب" / "Reject the application — the applicant will be notified with the reasons"; never a generic confirm.
5. **Rework discipline**: rework rounds render on the row and in the dossier (round 2 badge, prior decision chain); after the policy max (seeded 3), request-rework is contract-disabled (VALIDATION with the policy named — 07b rule 7) and the composer's guidance states the remaining options honestly.
6. **Disagreement with the machine**: when the abstract assessment suggests a verdict, the dossier renders it as INPUT (provenance + confidence-as-stated) beside the human's decision composer; a decision that diverges from the machine suggestion is not blocked, warned, or logged differently — the human decides, period (02 Maryam; Gradient Labs' "what to keep human" formalized, 01 §2).
7. **The dispute path (Sami's two-click test, 00 success signal 4)**: from any task (or the applicants directory), the LEDGER view assembles the complete chain — submissions, captures, quality reports, assessments with provenance, decisions with reason codes and notes, rework rounds, attestation with timestamp, every activity entry (P17). `listActivity` drives the view; `exportAuditLedger` (period- or application-scoped) is a Job producing the artifact with its expiry window (async-contract §2).
8. **Live queue behavior**: `subscribeApplicationEvents` patches rows in place (submitted → queue arrives; rework returned → flagged; SLA breach warnings) — reshuffles only off-viewport or on scroll-idle, never under the cursor; landings announce politely on the focused row only (09 schedule).
9. **Post-decision**: approved applications close with the notice; rejected applications retain their full evidence chain (retention policy, 12 Q-8); the outcome counters (queue depth, aging, decisions per day, rework rate) render on the queue header — operational counters only, no funnel analytics (LOOP-3 boundary with funnel-drop-off-explorer, 12 Q-5).

**Edge cases**: applicant withdraws mid-review → task resolves withdrawn with the withdrawal entry linked (no phantom decision); two reviewers open the same task → both dossiers render, second decision gets CONFLICT with both payloads shown (first-write wins, re-decide explicit); assessment capability returns late (job pending) → the dossier renders "التقييم الآلي قيد الجريان — يمكنك البت الآن على الأدلة" / "Automated assessment in progress — you can decide now on the evidence" (the machine is never a blocker — 07b rule 4); rework-submitted application arrives with a NEW capture that fails gates → the failure renders as a mismatch flag for the reviewer (the applicant was warned at capture; the reviewer sees both).
**Failure modes**: decideReviewTask VALIDATION (missing reason codes on reject/rework; rework beyond max; no step ids on rework) → the failing rule named inline; assignReviewTask PERMISSION (suspended reviewer) → lock state with restore path; getReviewTask NOT_FOUND (task decided underneath) → safe-state + queue re-sync; requestVerificationAssessment RATE_LIMIT (assessment spam guard) → window + reset; NETWORK → decisions queue offline (P20) and reconcile idempotently — never a double-decision.
**Recovery**: decisions are immutable; corrections are new ledger entries (reversal decisions exist in the reason-code catalog — "قرار مُعاد" / "reversed decision" — the chain keeps both, dispute-grade).

## CP-6 — The program spine, templates, people, and the resilience walkthrough (admin; console)

1. **Flow designer (R3)**: `getFlowProgram` renders the current program: ordered steps (identity micro-steps, document step with type catalog + sides, presence-optional step, review step, submit), validation rules per step, capture gate thresholds (the five gates with workspace-tunable values, defaults per 07c §2.1), session policy (idle 20m / absolute 60m / resume window 30d / nudge threshold 48h / nudge cap 3-per-24h), document type catalog (bilingual labels), reason-code catalogs, and retention policy. Every policy renders as the SAME sheets applicants and reviewers see (inspectability — 02 Khalid's black-box aversion).
2. **Versioned publish**: `updateFlowProgram` requires a preview declaration (affected scope: new applications only; in-flight applications continue under their started version — the versioning rule, 07a) and publishes version+1 with a ledger entry; the publish notice states the in-flight rule plainly. Threshold changes to capture gates display the seeded defaults' provenance ("قيم افتراضية مقترحة" / "spec-proposed defaults" — honest, 12 Q-6).
3. **Applicants directory (R4)**: `listApplicants` (search with Arabic normalization — rtl-rules §4) and `getApplicant` (application history trail with outcomes); PII bounded to what the flow collected (09 privacy posture); withdrawal and retention actions render with consequences named.
4. **Nudges from the directory**: `sendResumeLink` on an idling application (rate-guarded, CP-1.5); the console renders the copy-link/QR manual alternative beside the channel action (LOOP-5).
5. **Templates studio (R5)**: `listMessageTemplates` (submitted-notice, rework-request, decision-notice approve/reject, resume-nudge, session-expired); `upsertMessageTemplate` (bilingual AR/EN bodies with parameter slots, versioned); `previewMessage` renders the applicant view for a chosen application — per-locale direction, bidi isolation visible, parameters filled (06 TemplatePreviewSheet). Templates are DATA the engine composes; no AI writes applicant messages (conditionally-AI declaration scoped to capture assist).
6. **Assessment capability posture (R3 tab)**: the abstract verification assessment (08 N1) binding state renders in capability language ("محرك التقييم المرتبط" / "bound assessment engine" vs "غير مربوط — المراجعة اليدوية على الأدلة" / "unbound — manual review on evidence"); `requestVerificationAssessment` can be triggered per-application from the console when a bound capability exists (and runs engine-side at submission per policy); the manual alternative (reviewers read raw evidence) is the declared default posture — the product is complete without it (LOOP-5).
7. **Team (R6)**: `listUsers` / `inviteUser` / `updateUser` — two structural roles (reviewer / admin); role changes are ledger entries; suspension locks mutations with read-paths intact (PERMISSION classes, 07b).
8. **Notifications (P21 ladder)**: instant tier = rework returned (owning reviewer), SLA-breach warning (owner + admin), escalation; digest tier = submission batches, nudge deliveries, program publishes, artifact expiry warnings. `listNotifications` + `markNotificationsSeen`; tier control per class per user.
9. **Jobs & exports (R7)**: `getJob` / `retryJob` / `cancelJob` — ledger exports, assessment runs (when bound); retry scoped to failed items (async-contract §4); artifacts carry expiry windows with renewal.
10. **Full-day walkthrough (release-test fixture, 00 success signals 1+2)**: 21:40 Amal starts (program v2), completes identity micro-steps with autosave visible, opens document step, times out at 22:03 (warning announced at 22:01, extend offered) — application persists; 09:10 next day she resumes on a DIFFERENT device (token honored), prior answers recalled-marked, captures her Iqama front (glare fail named twice → passes), back (passes first try), presence step (purpose stated, alternative visible), reviews summary, attests (focus order full), submits 09:19 — active work 11m40s, inside the 14-minute patience band (01 §4.3); ReviewTask created, deadline 24h; 08:00 next morning Maryam's queue: 12 tasks ranked by deadline; she opens the dossier (four layers, zero navigation), approves 9, rejects 1 (reason codes selected, applicant notified), requests rework on 2 (steps named); one rework returns at 14:20 (flagged round 2, deadline adjusted, same-owner) and is approved at 14:22. Ledger check: every mutation in the chain — 47 entries. Then the degradation re-run: every capability unbound (assessment, assist, channel) — checklist-guided capture, manual evidence review, copy-pasted resume link — same day completes, same ledger discipline. Both runs replayed twice, byte-identical (07c §5).
11. **Offline discipline (P20)**: applicant-side drafts queue with per-field state; reviewer decisions queue with per-task state; reconciliation discards only legally-superseded writes, with notices (never phantom writes).
