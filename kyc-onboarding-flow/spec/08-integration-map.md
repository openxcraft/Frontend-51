## Risk flags (LOOP-7 style, for binding-time owners)

- **N1 assessment semantics**: assessments must arrive as TYPED inputs (fieldResults, documentFindings, provenance) — never as verdicts, never as auto-resolving state; a binding that implies decision authority violates LOOP-10 and 07b rule 4 outright. Confidence renders as input; a reviewer diverging from a machine suggestion is a first-class path, not an exception (02 Maryam). The provenance sentence ("an input for review — not a decision") is contractual copy in both locales (11 §D4).
- **N1 privacy boundary**: assessments consume declared evidence (captures, extracted field values) — never applicant contact identifiers or unrelated workspace data (ai-native-patterns §9; 09 privacy posture). The capability label is kind-not-vendor in every surface (credential-contract §2.3).
- **N2 assist boundary**: the assist reads FRAME METRICS (the declared CaptureMetrics shape) — never the document image content itself, never retained beyond the session; enrichment failures degrade to rule-gates within the same call (07b rule 3), and the provenance field is the applicant-visible honesty contract (ai-native-patterns §8).
- **N3 template integrity**: applicant-facing notices are the trust surface — a channel binding must not alter template content, must deliver both locales faithfully (bidi isolation preserved), and must never fabricate delivery state (`deliveredVia` is truthful or the binding is broken). Rate caps (nudge 3/day) apply to channel sends identically (07c §2.3).
- **N4 identity ≠ authorization**: an SSO binding changes who signs in, never what roles exist — the two-role model (reviewer/admin) is the product's permission grammar (04); owners should not expect ACL expansion at binding time.
- **N5 artifact custody**: exports carry expiry windows (async-contract §2); a destination binding changes transport, not retention policy — retention remains the workspace's declared posture (12 Q-8).

## Consent semantics (per credential-contract)

- Credential-class surfaces are console-side only (assessment capability, assist capability, message channel, identity source, artifact destination) presented in capability language — "يقيّم المستندات المقدَّمة تلقائياً" / "evaluates submitted documents automatically" — kind-not-vendor, masked by default, screenshot-safe by construction (credential-contract §2).
- Grant display precedes any save (credential-contract §4): each need's grant names the operation classes it unlocks (read submitted evidence / enrich capture guidance / deliver applicant messages / prove console identity / file export artifacts).
- **Applicant data minimality is structural**: the applicant entity carries contactRef, displayName, locale, step answers, and captures (07a) — no geolocation, no device fingerprints, no biometric templates retained (presence captures are images passed to N1 as evidence; retention per program policy). The N2 assist consumes frame metrics only. Data-use statements at entry and attestation are template copy, versioned data (11).
- Capability failures surface where the capability is used (the dossier's assessment layer reads the unavailable state with the manual-review line; capture guidance flips provenance mid-session without an error wall — CP-3 edge), never only in a settings graveyard (credential-contract §3).
