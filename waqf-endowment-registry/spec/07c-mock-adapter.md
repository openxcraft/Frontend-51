## Deterministic computation rules (EXACT — the product's core arithmetic, fixed thresholds)

1. **Allocation inputs**: the endowment's ledger entries with `period === target` and `reversesEntryId === undefined` whose own reversal does not exist (a reversed entry is excluded from arithmetic; its reversal row is not an amount — it is a mark). Policy version = current at run; beneficiary register snapshot = current at run.
2. **Totals**: `inflows = Σ inflow entries` · `expenses = Σ expense entries` · `adminCapped = min(Σ administration expenses, adminCapPct × inflows)` (capped expenses beyond the ceiling are reported in the worksheet as over-cap, flagged, never silently included) · `maintenanceAndOther = Σ maintenance + other expenses` (never capped) · `reserveApplied = reservePct × inflows` · `distributable = inflows − adminCapped − maintenanceAndOther − reserveApplied`.
3. **Lines**: for each beneficiary with eligibility 'active' and a recorded deed share: `computedAmount = floor(distributable × numerator / denominator)` in minor units — floor to the minor unit, so a rounding residue exists unless shares divide the distributable exactly. 'succeeded'/'suspended' beneficiaries produce HELD lines (state 'held', reason pre-filled from the eligibility record); **held amounts are never redistributed** — they stay unallocated in the ledger until eligibility resolves (a deed-assigned share is not the remainder's to take; the invariant is fiqh-honest and audit-honest).
4. **Remainder**: `remainder = distributable − Σ computedAmounts − Σ heldAmounts` — i.e. the rounding residue PLUS the deed's unassigned share mass (shares recorded below the whole). If `remainderRule.mode = 'residual-beneficiary'`, the residual-holder line receives `remainder` (rendered as the deed's designated destination); if 'carry-forward', the remainder line is named carry-forward and no entry is appended for it. If `distributable < minimumDistribution`, the whole distributable carries forward (honest state — the worksheet says so).
5. **Regression assertion (fixed)**: W-S period 2026-10 → inflows 4,320,000 · adminCapped 432,000 (exactly 10% — no cap overage) · maintenance 168,000 · reserve 216,000 (5%) · distributable 3,504,000 · computed lines: 438,000 (3/24) ×3 and 292,000 (2/24) ×4 and 146,000 (1/24) institution · Σ computed 2,628,000 · held 292,000 (B-6, stays unallocated) · remainder = 3,504,000 − 2,628,000 − 292,000 = 584,000 to "الفقراء والمحتاجون" (the deed's unassigned 4/24, residue zero at this scale) · recorded distribution total 3,212,000 · unallocated after commit 508,000 (reserve + held). Every run of `runAllocation(W-S, '2026-10')` reproduces these exact minor-unit figures — the determinism contract is a test, not a promise.
6. **Report sections**: openingBalance = unallocated balance at period start (recorded inflows − recorded distributions before the period's first entry) · ratios = adminCapped/inflows and Σ distributions/inflows (4 decimal places, rendered as percentages with the division shown) · variance = signed deltas vs the same period-type prior · ledgerPin = per-endowment last seq at generation.
7. **Share-sum gate**: `addBeneficiary`/`updateBeneficiary` refuse when `Σ shares > 1` — VALIDATION with the overflow fraction in `details.shareSum`.
8. **Seq rule**: `seq = last + 1` per endowment, monotonic, never reused; reversal entries take the next seq (they are entries too).
9. **Seal rule**: state machine draft → sealed, exactly once; CONFLICT carrying sealedAt on repeat; pin written at seal time.
10. **Delivery rule**: delivery on a line whose allocation is 'voided' → CONFLICT naming the void; delivery on a committed line always succeeds and is idempotent per line (retry returns the same delivery state).
