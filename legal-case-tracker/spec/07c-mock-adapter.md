## Deterministic computation rules (the whole engine — non-AI, specified exactly)

1. **Clock and day arithmetic**: the seeded clock is fixed above; `daysUntil = floor((eventDate − today) / 1 day)` computed on date strings at the clock's time-of-day (09:00, no timezone drift). Derived reads (countdowns, board, gate) recompute at read from the current clock — they are never stored.
2. **Countdown zones** (pure function of daysUntil + outcome presence): hearing WITH standing outcome → historical, never on the board; else daysUntil ≥ 15 → `far`; 4–14 → `near`; 1–3 → `imminent`; 0 → `today`; < 0 → `overdue`. Zones bind the 05 color contracts (green/amber/red/red-deep) and are always rendered zone-icon + day-count text + color, never color alone.
3. **Deadline generation** (fires on `createTimelineEvent` kind hearing, `recordHearingOutcome` with scheduledNextHearing, and matter creation when `stockRulesOn`): for each ACTIVE rule whose trigger matches (and whose practice-area scope includes the matter): `due = anchorDate + offsetDays` (anchor = hearing date / outcome date / matter openedAt); then `due = max(due, today + minLeadDays)` (the clamp); then weekend shift — if `due` falls Fri or Sat and policy is `next-business-day`, advance to the following Sunday. Generated DeadlineEvents carry `ruleId` + `sourceTriggerEventId`. **Forward-only regeneration**: rule edits/deactivations regenerate only generated deadlines that are neither completed nor past-due; completed and past deadline events are history and stay (07a).
4. **Hearing board** (cross-matter, `listHearingBoard`): every hearing without a standing outcome where `date ≤ today + withinDays` (default 30), PLUS every overdue hearing (date < today, no outcome) regardless of horizon. Sort: `date` ascending (overdue rows first by recency); `zone` sort is far→near→imminent→today→overdue then date. Pagination stable per clock tick.
5. **Custody chain sequencing**: `seq` = previous + 1, contiguous from 1; `registerDocument` seeds `received` (when `isOriginal`, with the provenance note) then `registered`; `version-added`/`sealed`/`checked-out`/`checked-in`/`presented`/`returned`/`annotated` append per 07b signatures. `presented` requires `linkedEventId` (a hearing event) — VALIDATION without it. `returned` is the only entry that clears `unreturnedOriginal`.
6. **Chain verification** (`verifyChain`): recomputes the expected per-entry fingerprint table (each seeded/appended version's declared `contentFingerprint`; entries carry `versionId` where version-scoped); returns `intact: true` + `verifiedEntryCount`, or `intact: false` + `firstBrokenSeq` (failure injection `breakChainAtSeq` mutates the table copy, never the chain itself — the fixture proves detection, not corruption).
7. **Closure gate evaluation** (pure function over live matter state): blockers in order — every hearing with date ≥ today and no standing outcome (`future-hearing`); every hearing with date < today and no standing outcome (`outcome-due-hearing`); every incomplete deadline event (`open-deadline`); when `requireOriginalTracking`, every original document without a `returned` entry (`unreturned-original`). `closeMatter` evaluates this gate; any blocker → VALIDATION with `details.blockers[]` naming each with its bilingual label; success writes the immutable ClosureRecord.
8. **Outcome side-effects**: `recordHearingOutcome` writes the outcome; `scheduledNextHearing` creates the next hearing event (same court/parties context, date verbatim) and fires rule 3; corrections append via `correctionOfOutcomeId` and mark the old outcome `supersededBy` — no field of the old record is rewritten. The returned TimelineEventView carries the recomputed countdown, the new event, and the outcome history.
9. **Determinism oracle**: identical call sequences from `reset()` produce identical state hashes; scans of derived reads (board, gate, zones) are pure re-derivations — the mock's own regression test.

## Behavior (per operation class)

- `createMatter` — empty `title.ar` or `title.en` → VALIDATION naming the field (bilingual-by-construction rule); `firstHearing` present → event created + hearing-created rules fire; `stockRulesOn` true → matter-opened rules fire (rule-006 inactive → demonstrably does NOT fire).
- `listMatters` / `listTimelineEvents` / `listDocuments` / `listClients` — normalized bilingual search (rtl-rules §4 pipeline, disclosed in-product); filters declared as removable chips (P08); urgencyZone filter exercises zone arithmetic live.
- `updateMatter` — stage patch to `'closed'` → VALIDATION redirecting to `closeMatter` (the gate is the only path); stale `baseVersion` → CONFLICT with both payloads.
- `closeMatter` — gate rule 7; success writes ClosureRecord + activity; a later mutation on the closed matter (e.g. a note event) re-opens `stage: 'active'` with a pending-activity flag; the record and the export's `closedMatterVersion` stay untouched.
- `updateTimelineEvent` — reschedule without `reason` → VALIDATION; with reason → RescheduleRecord appended, date updated, hearing-created rules re-evaluated for the NEW date (forward-only, rule 3); stale baseVersion → CONFLICT.
- `recordHearingOutcome` — empty either language of `summary` → VALIDATION; standing outcome exists without `correctionOfOutcomeId` → CONFLICT naming it; with correction id → append + supersede; scheduledNextHearing → rule 8 side-effect. The gavel (05) fires in the UI on the returned view.
- `completeDeadlineEvent` — completion writes `completedAt` + `completedByMemberId`; completing an already-completed deadline → CONFLICT showing the completion record (facts are not silently re-facts).
- `listHearingBoard` — rule 4; prep-deadline column joins the nearest incomplete generated pre-hearing deadline per row.
- `saveDeadlineRule` — sanity: `offsetDays ≥ 0` with trigger `hearing-created` → VALIDATION (prep rules are negative by definition); `minLeadDays < 0` → VALIDATION; stale baseVersion → CONFLICT; edit regenerates future generated deadlines only (surfaced in the result, never silent).
- `deleteDeadlineRule` — requires `confirm.openGeneratedDeadlines` matching the live count → else VALIDATION; on delete, open generated deadlines from the rule remain (pinned to the deleted rule id — audit honesty) and close only by completion.
- `registerDocument` — idempotency key replay returns the original DocumentView; seeds chain per rule 5.
- `addDocumentVersion` — appends version (seq = last + 1) + `version-added` entry; a version after a sealed version is a NEW lineage node (sealed nodes never mutate).
- `sealDocumentVersion` — already sealed → CONFLICT showing the sealing entry; success appends `sealed` + activity.
- `addCustodyEntry` — `presented` without `linkedEventId` → VALIDATION; `returned` on a non-original → VALIDATION (only originals return); append-only per rule 5.
- `verifyChain` — rule 6; `breakChainAtSeq` injection returns `intact: false` + the named seq.
- `exportMatterPackage` — artifacts expire at creation + 7 days; `regenerable: true` always; `failExportFormat` injection fails the named format after the others deliver (partial policy); idempotent re-submit returns the original job; closed matters carry `closedMatterVersion` and flag later activity.
- `getArtifact` — expired → NOT_FOUND with the regenerate path; matter state unchanged by regeneration (deterministic from state).
- `getUsage` — fixed window with seeded export count; `quotaExhausted` injection → RATE_LIMIT ladder copy (11).
